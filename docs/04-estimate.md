# 시간과 비용을 어떻게 답하는가 (2026-08-31)

**사용자는 아무것도 재지 않는다.** 서버가 재고 답만 갱신한다. 진행률 표시와 같다.

---

## 1. 스텝 수는 계산으로 정확히 나온다

학습 script 가 정해 놓은 값 둘을 읽으면 된다.

```
스텝 수 = ceil(학습 쌍 ÷ (per_device_train_batch_size × gradient_accumulation_steps)) × 에폭
```

우리 script 는 `1 × 8 = 8` 이다 (`train_dpo_m3.py:91`). **실행 8 건 모두 로그와 정확히
일치했다.**

| 작업 | 쌍 | 계산 | 로그 |
|---|---|---|---|
| telecom 실험1 | 564 | ceil(564÷8)×4 = 284 | 284 |
| telecom 실험2 | 675 | 340 | 340 |
| bank 실험1 | 973 | 488 | 488 |
| bank 실험1' | 1,061 | 532 | 532 |
| market 실험2 | 742 | 372 | 372 |
| AIOps 실험1 | 3,311 | 1,656 | 1,656 |
| bank 실험2' | 1,110 | 556 | 556 |
| AIOps 실험2 | 3,546 | 1,776 | 1,776 |

**여기에는 오차가 없다.**

## 2. 스텝당 시간은 재야 한다

### 초/스텝 대신 토큰/초를 쓴다

초/스텝은 문장 길이에 따라 흔들린다. 토큰/초로 재면 그 영향이 상당 부분 빠진다. 학습 로그
마지막 줄의 `num_tokens ÷ train_runtime` 이다.

| 작업 | GPU | 캡 | 한 행 길이 | 토큰/초 |
|---|---|---|---|---|
| telecom 실험1 | L40S | 12288 | 4,144 | 1,505 |
| telecom 실험2 | L40S | 12288 | ~4,000 | 1,495 |
| bank 실험1 | L40S | 12288 | ~4,100 | 1,480 |
| bank 실험1' | L40S | 12288 | 4,144 | 1,474 |
| **bank 실험2'** | L40S | 12288 | ~4,100 | **1,555** |
| **market 실험2** | L40S | **18432** | 10,619 | **1,000** |
| AIOps 실험1 | A100-SXM4-80GB | 12288 | ~5,600 | 1,682 |
| **AIOps 실험2** | L40S | 12288 | ~5,600 | **1,357** |

### 그래도 완전히 빠지지는 않는다

**같은 L40S 인데 캡 12288 에서 1,474 이고 18432 에서 1,000 이다. 32% 떨어진다.**
attention 계산이 문장 길이의 제곱으로 늘기 때문이다.

두 측정점으로 `시간 = a×L + b×L²` 를 맞추면 이렇게 나온다.

```
  a = 4.7215e-04 (길이에 비례하는 몫), b = 4.9738e-08 (제곱에 비례하는 몫)
  한 행  4,144 토큰 -> 선형 69.6% / 제곱 30.4%
  한 행 10,619 토큰 -> 선형 47.2% / 제곱 52.8%
```

**미지수 둘에 측정점 둘이라 두 점을 지나는 선을 그은 것이지 검증된 모형이 아니다.**
세 번째 길이에서 재보면 어긋날 수 있다.

## 3. 제출 전 — 범위와 근거를 함께 답한다

| `confidence` | 뜻 | 답하는 것 |
|---|---|---|
| `measured` | 같은 GPU, 비슷한 길이를 이미 쟀다 | 좁은 범위. "6.5 ~ 7.5시간, 폭 2.1%" |
| `interpolated` | GPU 는 같은데 길이가 다르다 | 넓은 범위. "18 ~ 34시간" |
| `unknown` | 처음 보는 조합 | **범위 대신 "실행 35분 뒤 확정"** |

**틀린 숫자 하나보다 `unknown` 이 낫다.** market 을 9.14 시간으로 답했다가 17.87 시간이었다.
96% 틀렸다.

## 4. 제출 후 — 서버가 스스로 갱신한다

학습 라이브러리가 진행 줄에 스텝당 시간을 이미 찍는다.

```
350/556 [4:02:35<2:22:44, 41.57s/it]
        └ 경과      └ 남은 시간   └ 스텝당
```

서버가 이 줄을 읽어 `/jobs/{id}` 응답에 넣는다. **사용자는 아무 일도 하지 않는다.**

```
제출 직후    예상 29 ~ 38시간   근거: 미측정
35분 뒤      예상 31.6시간      근거: 200스텝 실측
6시간 뒤     남은 25:45         진행 17%
```

### 초반에는 흔들린다 — 50 스텝을 기준으로 삼는다

`bank-exp2v2` 가 실제로 어떻게 움직였다.

```
    1스텝    56.00s/it  ->  전체  8.65h  $ 8.56
    5스텝    45.74s/it  ->  전체  7.06h  $ 6.99
   50스텝    40.61s/it  ->  전체  6.27h  $ 6.21
  300스텝    39.06s/it  ->  전체  6.03h  $ 5.97
  최종     42.32s/it  ->  전체  6.54h  $ 6.47
```

**1 스텝에서는 32% 틀렸다.** 50 스텝쯤부터 최종값 근처로 안정된다. bank 기준 35 분이다.

### 긴 작업은 끝까지 흔들린다 — 그래서 범위로 보여 준다

`aiops-exp2` 는 1,776 스텝인데 이렇게 움직였다.

```
    1스텝    72.48s/it  ->  전체 35.76h
  200스텝    64.13s/it  ->  전체 31.64h
  600스텝    58.38s/it  ->  전체 28.80h
  800스텝    77.46s/it  ->  전체 38.21h
 1200스텝    66.72s/it  ->  전체 32.92h
  최종      66.44s/it  ->  전체 33.53h
```

**28.80 시간에서 38.21 시간까지 33% 폭으로 오간다.** 원인은 확인하지 못했다. 표본 길이가
구간마다 다르거나, checkpoint 를 쓰는 동안 멈추거나, 같은 서버의 다른 작업 때문일 수 있다.

## 5. VRAM 은 계산으로 답할 수 있다

터지는 것은 attention 이 아니라 **마지막 logits** 이다.

```
logits 크기 = 2(chosen/rejected) × 문장길이 × vocabulary × 2바이트
Qwen3-4B 는 vocabulary 151,936 이므로 토큰 하나가 297 KiB
```

| 한 행 길이 | logits |
|---|---|
| 4,000 | 2.26 GiB |
| 8,000 | 4.53 GiB |
| 11,926 | 6.75 GiB  <- L40S 48GB 에서 터진 값 |
| 18,432 | 10.43 GiB |

**L40S 48GB 의 실사용 가능량이 44.39 GiB 다.** AIOps 실험1 이 터졌을 때 3.43 GiB 만 남아
있었고 6.75 GiB 를 요청했다.

### 완화 수단 둘을 먼저 권한다

| 수단 | 하는 일 | 학습 결과 |
|---|---|---|
| `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` | 단편화 방지 | **안 바뀜** |
| `patch_trl_liger_slice.py` | logits 를 답변 구간만 만듦 | **안 바뀜** (문서 주장) |

**둘을 켜니 AIOps 가 L40S 에서 돌았다.** 실험1 은 같은 L40S 에서 4 스텝 만에 죽었는데
실험2 는 완주했고 스텝당 시간도 85.90 초에서 66.44 초로 22.7% 빨라졌다.

## 6. 어느 GPU 를 권할 것인가

우리 실측으로 A100 과 L40S 를 비교하면 이렇다.

| | GPU | 시간당 | 스텝당 | 총 비용 |
|---|---|---|---|---|
| AIOps 실험1 | A100-SXM4-80GB | $1.59 | 53.49초 | $40.21 |
| AIOps 실험2 | **L40S** | **$0.99** | 66.44초 | **$33.20** |

**A100 이 1.24 배 빠른데 단가가 1.61 배 비싸다.** 완화 수단을 켜서 L40S 에 들어가면
L40S 가 싸다.

권고 규칙은 이렇다.

```
1. logits 계산으로 필요 VRAM 을 낸다
2. 완화 수단 둘을 켠 값으로 다시 낸다
3. 48GB 에 들어가면 L40S,  안 들어가면 80GB
4. 확신이 없으면 80GB.  A100 이 그만큼 빠르므로 큰 손해가 아니다
```

## 7. spot 과 on-demand

**RunPod 은 spot 을 팔지 않는다.** decider 가 `capacityType != "on-demand"` 면 카탈로그를
읽기 전에 거절한다 (`pkg/decider/runpod/decider.go:242`). 그리고 **PACSrun 의 기본값이
spot 이다** (`pkg/decider/decider.go:287-288`).

**즉 `capacityType: on-demand` 를 안 적으면 RunPod 이 후보에서 빠진다.** 서버가 반드시
채워야 하는 자리다.

| 조건 | 권고 |
|---|---|
| RunPod 을 쓴다 | `on-demand` 고정. 선택지가 없다 |
| 4시간 미만, checkpoint 없음 | spot 가능 |
| 4시간 이상, checkpoint 있음 | spot 가능. 복구가 성립한다 |
| **4시간 이상, checkpoint 없음** | **on-demand.** 20시간째에 뺏기면 전부 잃는다 |

## 8. 끝나면 측정표에 쌓는다

job 이 끝날 때마다 `(GPU, 캡, 한 행 길이, 토큰/초, 완화수단)` 한 줄이 는다. 지금 8 개다.
**쓸수록 `unknown` 답이 줄어든다.**
