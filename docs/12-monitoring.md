# 4단계 — 무엇이 도는지 보는 법 (2026-08-31)

`08-plan.md` 의 4단계입니다. `05-monitoring.md` 가 화면 넷을 설계했고, 그 화면들이 읽을
뒷단을 여기서 만들었습니다.

## 만든 것

```
server/ddpsrun_server/metrics.py   DDPSRUN-METRICS   로그에서 두 줄 모양을 뽑는다
server/ddpsrun_server/k8s.py       recent_log_lines  시간 창으로 로그를 읽는다
server/ddpsrun_server/main.py      GET /v1/jobs/{id}/metrics
cli/ddpsrun/cli.py                 ddpsrun watch
agent/references/script-contract.md  8 번 항목: run.sh 가 찍을 것
```

## 결정 하나 — 아무것도 저장하지 않습니다

**시계열을 저장하지 않기로 했습니다.** 지표 endpoint 를 만들 때 자연스러운 모양은 시계열
저장소이고, 그러면 **서버가 처음으로 상태를 들게 됩니다.** 백업할 것, 크기를 정할 것,
그리고 잘렸을 때 로그와 어긋나는 것이 생깁니다.

그런데 그 값들은 **이미 로그에 있습니다.** `run.sh` 가 30 초마다 한 줄 찍고, 학습
라이브러리가 자기 진행 줄을 찍고, 둘 다 driver 가 중계하는 같은 stdout 을 탑니다.
`read_namespaced_pod_log` 는 `since_seconds` 를 받으므로
**한 조각만 읽는 것이 쌉니다.**

**대가는 분명합니다.** pod 이 garbage-collect 되면 지표도 로그와 함께 사라집니다. 끝난 job 의
그래프는 없습니다. 이것은 로그가 원래 그런 것이지 새로 생기는 제약이 아니지만, 감춰 두면 안
되는 한계입니다.

## 읽는 줄 두 가지

**첫째, `run.sh` 가 찍는 GPU 줄입니다.** `script-contract.md` 8 번이 그 네 줄을 줍니다.

```
PACSRUN_GPU=94,38200,45440,71,298.5
             │  │     │     │  └ power.draw (W)
             │  │     │     └ temperature.gpu (C)
             │  │     └ memory.total (MiB)
             │  └ memory.used (MiB)
             └ utilization.gpu (%)
```

`nvidia-smi` 는 **그 machine 안에서만 실행됩니다.** 원격 컨테이너에는 들어갈 수 없고
(`kubectl exec` 는 EKS 의 pod 에만 통합니다) 나오는 것은 stdout 한 줄기뿐이라, script 가
스스로 찍어 보내는 것 말고는 방법이 없습니다. `05-monitoring.md` 의 A, B, C 중 B 입니다.

**둘째, 학습 라이브러리가 이미 찍는 진행 줄입니다.**

```
 63%|######3   | 350/556 [4:02:35<2:22:44, 41.57s/it]
                  │   │   │        │        └ 스텝당 (running average)
                  │   │   │        └ 남은 시간
                  │   │   └ 경과
                  │   └ 전체 스텝
                  └ 끝난 스텝
```

## 왜 `/estimate` 가 있는데 이것도 읽는가

**`/estimate` 는 남의 실행에서 만든 답이고, 이것은 이 실행 자신의 답입니다.** 50 스텝쯤부터는
이쪽이 낫습니다.

bank-exp2v2 가 실제로 이렇게 움직였습니다. 최종은 6.54 시간이었습니다.

| 스텝 | 스텝당 | 그 시점의 예상 | 최종 대비 |
|---|---|---|---|
| 1 | 56.00 초 | 8.65 시간 | 32% 틀림 |
| 5 | 45.74 | 7.06 | 8% |
| 50 | 40.61 | 6.27 | 4% |
| 300 | 39.06 | 6.03 | 8% |

그래서 **50 스텝 미만이면 `steady: false` 로 표시하고 그 값을 사실처럼 쓰지 않습니다.**
`ddpsrun watch` 는 "아직 안 정해짐" 을 붙여서 보여 줍니다.

**긴 job 은 끝까지 흔들립니다.** aiops-exp2 는 1,776 스텝인데 자기 예상이 28.80 에서 38.21
시간까지 33% 폭으로 오갔습니다. 원인은 확인하지 못했습니다. 그래서 화면에도 범위를 같이
보여 주어야 합니다.

## 같은 줄을 두 endpoint 가 반대로 다룹니다

- `/v1/jobs/{id}/metrics` 는 `PACSRUN_GPU=` 를 **읽으려고** 존재합니다.
- `/v1/jobs/{id}/logs` 는 그 줄을 **통째로 버립니다.** 사용자 출력이 아니고, 30 초마다
  나오므로 학습 로그 사이에 계속 끼어듭니다.

그래서 로그를 읽는 함수는 거르지 않고, **거르는 일은 쓰는 쪽에서 합니다.**

처음에는 `PACSRUN_KEEPALIVE` 처럼 버리지 않고 `<internal>` 로 가리기만 했는데, 결과가
이랬습니다.

```
{'loss': 0.428, 'epoch': 3.93}
 21%|###########   | 354/556 [7:58:00<2:22:44, 41.57s/it]
<internal>=97,38380,45440,72,304.0
{'loss': 0.424, 'epoch': 3.97}
```

**keepalive 규칙이 막으려던 것과 똑같은 잡음입니다.** 두 endpoint 를 같은 로그에 붙여
돌려 보다가 찾았습니다.

## 써 보는 모습

```
$ ddpsrun watch job-5ef19d1af06d
  학습        #############-------  357 / 556 스텝  (64.2%)
              41.57 초/스텝, 7:59:00 경과, 2:22:44 남음
  예상 총계   6.42 시간
  GPU 사용률  ###################-  97%
  메모리      #################---  38,380 / 45,440 MiB (84.5%)
  온도, 전력  72 C, 304.0 W
  표본        120 개, 최근 3600초
```

**메모리 줄이 가장 중요합니다.** AIOps 실험1 이 L40S 48GB 에서 메모리로 죽었는데, 이 값이
100% 에 다가가는 것이 보였다면 4 스텝 전에 알았을 것입니다.

## 창과 표본 수

- 창은 기본 3,600 초이고 최대 86,400 초입니다. **상한이 없으면 요청 하나가 25 시간짜리 로그
  수십만 줄을 몇 초마다 읽습니다.**
- 표본은 400 개로 줄여서 보냅니다. 25 시간짜리 job 이 3,000 개를 찍는데 800 픽셀짜리 그래프가
  그보다 많이 못 보여 줍니다. **마지막 표본은 항상 남기므로 그래프가 job 의 현재 위치에서
  끝납니다.**

## 답이 비어 있을 때 이유를 말합니다

"데이터 없음" 과 "당신의 script 가 안 찍는다" 는 사용자에게 똑같아 보이는데 고치는 방법이
다릅니다. 그래서 `note` 로 구분합니다.

| 상황 | note |
|---|---|
| 둘 다 없다 | 아직 계산을 시작 안 했거나 script 가 안 찍는다. 계약 8 번을 보라 |
| 진행 줄만 있다 | `PACSRUN_GPU=` 감시가 없다 |
| GPU 줄만 있다 | 아직 설치나 모델 다운로드 중일 수 있다 |
| 둘 다 있는데 50 스텝 미만 | 예상이 아직 안 정해졌다 |

## 확인 안 된 것

1. **실제 job 에 붙여 본 적이 없습니다.** 지금까지 돌린 8 건의 `run.sh` 에는
   `PACSRUN_GPU=` 감시가 없었습니다. 다음 job 부터 계약 8 번을 넣어야 첫 실측이 됩니다.
2. **`since_seconds` 로 읽는 비용을 재본 적이 없습니다.** 35 만 줄짜리 로그에서 한 시간
   창을 읽는 데 얼마나 걸리는지 모릅니다.
3. **화면은 없습니다.** 지금 있는 것은 endpoint 와 `ddpsrun watch` 뿐이고,
   `05-monitoring.md` 의 화면 넷은 6단계입니다.
